# Описания элементов и сноски полей

## Негативный промпт

Не писать описания на английском языке. Не упоминать Codex, автора-ассистента
и англоязычные служебные метки в описаниях элементов Alterios. Не подменять
подробное назначение общими фразами, названием элемента или меткой автоматизации.
Не добавлять постоянные сноски к полям, отличным от типа «Дата». Не создавать
сноску у даты автоматически: она нужна только для пояснения ввода. Не помещать
технические ID и административное описание в сноски. Не выдумывать ID, связи,
назначение и свойства API.

## Обязательное содержание описания

Для каждого создаваемого или изменяемого элемента описывать по-русски:

1. Назначение и решаемую задачу.
2. Где используется, кем открывается или каким событием вызывается.
3. Входные данные, правила обработки, результат и изменяемые данные.
4. Фактические связи: **вид элемента — название — точный ID — роль связи**.

Для скриптов указывать инициатор, аргументы, читаемые и изменяемые типы
материалов и поля, связанные формы, вызываемые библиотеки и результат.
Для форм — сценарий работы, источники данных, встроенные представления,
действия, вызываемые скрипты и переходы на другие формы.
Для полей — смысл значения, владелец, правила заполнения и целевые связи.
Для представлений — источники, соединения, фильтры и потребляющие формы/отчёты.
Для отчётов и процессов — источники, параметры, вызываемые скрипты, формы задач
и результат. Для остальных элементов использовать те же четыре раздела
в объёме, соответствующем их роли.

ID брать из конфигурации или подтверждённых ответов API. Если связанные элементы
только создаются, получить ID, дополнить описания в пределах согласованной
работы и повторно прочитать сохранённое. Заглушки не сохранять. Если связи
не проверены, прямо указать это, не утверждая, что связей нет.
Точные ID, mname, ключи API, имена функций и форматы дат сохранять без перевода.

Если отдельного поля описания нет, документировать дочерний элемент в описании
ближайшего поддерживаемого родителя с точным путём дочернего элемента.
Не добавлять неподдерживаемые свойства API и не менять посторонние элементы.

Описание, всплывающая подсказка и постоянная сноска — разные свойства.
Описание не дублировать под полем. Это правило не отменяет существующие
требования к всплывающим подсказкам и не требует добавлять сноски ко всем датам.

## Применение в MCP

Правила передаются клиенту в инструкциях сервера при подключении и возвращаются
инструментом `alterios_ux_contract` в `authoring_instructions`. Клиент должен
следовать им при подготовке записей. Они не являются автоматической проверкой
истинности назначения, языка или всех перечисленных связей.

Сноски проверяются существующим кодом `field_footnote_requires_date`;
строгая проверка формы блокирует подтверждённое нарушение. Приёмка включает
чтение сохранённых описаний через API и проверку сносок в форме.

Новые стандартные метки автоматизации записываются по-русски. Старая метка
распознаётся для совместимости проверок принадлежности. Это не разрешает её
добавлять в новые описания. Существующие описания и явно переданные значения
массово не переписываются; автор должен подготовить новый текст по этим правилам.
