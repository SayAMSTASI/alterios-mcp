# Ограничение ответов и ускорение чтения

Версия 0.4.0 добавляет пять оптимизаций. Проверки записи, согласованных планов,
профиля, проекта, принадлежности объектов и актуальности сервера сохранены.

## 1. Компактные ответы

`alterios_read_all_objects`, `alterios_find_usages`, `alterios_relation_graph`,
`alterios_diagnose_view`, `alterios_audit_log`, `alterios_list_notifications` и
`alterios_list_files` по умолчанию возвращают `response_mode="compact"`:

- не более `preview_rows=20` элементов на коллекцию;
- стандартный набор идентификаторов, названий и диагностических полей;
- длинные строки и глубоко вложенные значения сокращаются;
- полный очищенный результат сохраняется в приватном `read-results/*.json`;
- `presentation.artifact` содержит путь, размер и SHA-256;
- `max_response_bytes=16384` ограничивает JSON-ответ, включая метрики.

При превышении бюджета предпросмотр заменяется квитанцией файла. Отдельные
статусы полноты исходного чтения сохраняются. `presentation.truncated` относится
к отображению: не путать его с `complete`, `complete_within_snapshot` или
ограничением вычисленного графа `truncated`. Полный файл содержит весь результат
в пределах заданных лимитов чтения, а не все данные сервера без ограничений.

У списков объектов, журнала, уведомлений и файлов параметр `fields` выбирает
буквальные имена полей верхнего уровня у строк предпросмотра. Он не меняет
серверный запрос и не удаляет поля из полного файла. Предельное количество
строк предпросмотра — 100, размер ответа — 256 КиБ, минимальный бюджет — 4 КиБ.

`response_mode="artifact"` оставляет сводку и файл. `response_mode="full"`
возвращает полный результат только если тот помещается в бюджет; иначе
возвращается компактный результат с причиной переключения.

**Совместимость:** потребителям, ожидавшим все строки непосредственно в `rows`,
нужно явно выбирать `full` и проверять `presentation`, либо читать файл.
Старые низкоуровневые инструменты, не перечисленные выше, сохраняют свои ответы.
Приватные результаты не публиковать; автоматическое удаление старых файлов
этот выпуск не выполняет.

## 2. Адресный preflight

Пример параметров `alterios_live_task_preflight`:

```json
{
  "profile": "example",
  "project_id": "target-project-id",
  "scenario_tool": "typed_write",
  "health_scope": [{"kind": "fields", "id": "confirmed-field-id"}],
  "scope_max_objects": 50,
  "scope_max_depth": 3
}
```

Остальные обязательные параметры проверки, включая подтверждения работы,
остаются применимы. Пример — схема аргументов, а не готовое разрешение записи.

Адресный режим свежими запросами читает точные формы, представления, поля,
типы материалов, скрипты, отчёты и схемы процессов. Проверяет совпадение ID
ответа и `projectId`, если сервер его вернул; формы проверяет строгим UX-контрактом.
Для представлений дополнительно читает сущности и колонки. По известным
структурированным ссылкам `formId`, `viewId`, `contentTypeId`,
`contentTypeFieldId`, `scriptId`, `manualScriptId`, `librariesIds`, `reportId`,
`diagramId` обходит исходящие зависимости. Повторные ID не перечитываются.

Ограничения: до 100 объектов, глубина до 8 и до 32 ссылок на единицу бюджета
объектов. Ошибки, неправильный ID/проект и исчерпание бюджета блокируют результат,
включая случай `require_clean_health=false`. Общие элементы другого проекта
тоже блокируются: межпроектное разрешение не подразумевается.

Успех обозначается **`ready_within_scope`**, а `full_project_verified=false`.
Этот режим не проверяет входящие использования, вычисляемые ссылки в коде,
семантику BPMN/отчётов, бизнес-результаты и права пользователей. Другие известные
зависимости следует явно включать в `health_scope`. Внутри лимитов проверяется
существование объектов и поддерживаемые связи, а не все свойства каждого типа.

Режим доступен только при `scenario_tool="typed_write"` и включённых проверках
состояния. Для массовых действий, удаления и сценариев создания модулей сохраняется
проверка всего проекта. Адресный результат не подменяет обязательные проверки
самого инструмента записи. Без `health_scope` прежнее поведение не меняется.

## 3. Параллельные чтения

У `alterios_export_dataset` появился `detail_workers=4` (от 1 до 8).
Параллельно читаются только независимые полные объекты при `include_details=true`.
Страницы, виды объектов, общий лимит строк и резервирование бюджета деталей
обрабатываются последовательно. Порядок объектов и ошибок стабилен.
Ошибки чтения сохраняются, а снимок остаётся неполным. Количество HTTP-запросов
от распараллеливания не уменьшается. Для нагруженного сервера выбрать 1–2 потока.

## 4. Индекс снимка

Поиск и граф используют общий кеш разобранного локального снимка, нормализованных
строк поиска и связей. Связная область графа ищется обходом соседей вместо
повторного просмотра всех рёбер. Кеш ограничен четырьмя записями, временем
300 секунд и консервативной оценкой веса 64 МиБ с резервом для графов;
это не обещание точного ограничения RSS всего процесса Python.
Большие снимки обрабатываются без сохранения индекса в кеше.

Ключ включает абсолютный путь, профиль и проект. Проверяются размер и файловые
метаданные; изменённый файл перечитывается. `refresh_cache=true` заставляет
перечитать локальный файл. Снимок неизменяем по договорённости; кеш не предназначен
для защиты от злоумышленника, сохраняющего все файловые метаданные.
Обновление кеша **не обновляет данные Alterios**: для этого нужен новый экспорт.
Попадание в кеш отражается в `cache.hit` и компактной квитанции.

## 5. Метрики и воспроизводимые замеры

Оптимизированные сценарии возвращают `metrics`: длительность, число обычных
HTTP-запросов через транспорт клиента, ошибки, суммарное время HTTP и размер
JSON-ответа в байтах UTF-8. При параллельной загрузке сумма времени HTTP может
превышать длительность операции. Метрики не собирают URL, заголовки или секреты.
Это время выполнения функции, без очереди клиента и передачи MCP-ответа;
размер протокольной оболочки MCP не входит в счётчик. Скачивание бинарных файлов
и сторонние транспорты не включены в эти счётчики.

```powershell
python scripts/benchmark_read_workflows.py --repeats 5 --output artifacts/performance.json
```

Скрипт сравнивает одинаковые локальные результаты, кеш и старый алгоритм поиска,
один/четыре потока, размер ответа и реальные вызовы функций инвентаризации на
искусственном клиенте. Ключи доступа не нужны. CI запускает один повтор и
проверяет корректность; нестабильные пороги времени не блокируют сборку.

Один локальный запуск (2 000 строк; 32 детальных объекта; искусственная задержка
5 мс на детальный запрос; медианы пяти повторов):

| Проверка | До / исходный режим | Оптимизированный режим |
|---|---:|---:|
| Ответ со строками | 3 266 026 байт | около 1,2 КБ и файл |
| Поиск без совпадений | 23,8 мс с чтением JSON | 1,0 мс с прогретым индексом |
| Связная область цепочки | 380,8 мс | 1,6 мс с прогретым графом |
| Детальные чтения | 180,6 мс, один поток | 48,3 мс, четыре потока |
| Количество детальных запросов | 33 | 33 |
| Проверка состояния | 46 запросов по всему тестовому проекту | 2 по полю и его типу |

Охват двух последних вариантов проверки состояния различается намеренно.
Холодный индекс поиска в том же запуске строился около 27,5 мс. Граф строился
впервые на уже разобранном снимке около 5,8 мс. Сохранение компактного ответа
вместе с полным файлом занимало около 106 мс. Эти результаты не являются
измерениями промышленного сервера, гарантией ускорения или SLA.

Также устранён дорогой повторный обход при маскировании и перебор начала ключа
на каждой позиции длинной строки. Проверки вложенных секретов сохранены.
